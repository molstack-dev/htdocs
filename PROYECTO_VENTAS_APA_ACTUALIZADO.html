Resumen

Chef Jonathan Buitrago es una aplicación web orientada a la oferta y administración de cursos, asesorías y eventos de pastelería. La solución permite a los visitantes consultar el catálogo; a los usuarios registrados, crear su cuenta, gestionar su perfil, agendar servicios, cargar comprobantes de pago, consultar el historial, acceder al contenido de cursos pagados y solicitar reembolsos; y a los administradores, gestionar usuarios, cursos, contenido formativo, solicitudes de servicio e incidencias de reembolso. La implementación revisada se compone de páginas HTML, hojas de estilo y JavaScript del lado del cliente, además de una API PHP que se comunica con una base de datos MySQL mediante PDO. La autenticación usa sesiones PHP y las contraseñas se almacenan con funciones de hash. Este documento sustituye afirmaciones no respaldadas por el código —como SQLite, inventario, facturación electrónica, infraestructura cloud o lectores de códigos de barras— por la funcionalidad verificable en el repositorio.

Palabras clave: sistema web, cursos de pastelería, PHP, MySQL, inscripciones, asesorías.

Abstract

Chef Jonathan Buitrago is a web application for offering and administering pastry courses, advisory services, and events. Visitors can browse the catalog; registered users can create an account, manage their profile, schedule services, upload payment receipts, review their history, access paid course content, and request refunds; administrators can manage users, courses, learning content, service requests, and refund cases. The reviewed implementation consists of HTML pages, client-side CSS and JavaScript, and a PHP API connected to a MySQL database through PDO. Authentication relies on PHP sessions and passwords are stored using hashing functions. This document replaces unsupported statements—such as SQLite, inventory management, electronic invoicing, cloud infrastructure, and barcode readers—with functionality verified in the repository.

Keywords: web system, pastry courses, PHP, MySQL, registrations, advisory services.

Introducción

La presencia digital facilita que un negocio de formación y servicios gastronómicos divulgue su oferta, reciba solicitudes y haga seguimiento a los servicios vendidos. El proyecto Chef Jonathan Buitrago responde a esta necesidad mediante una aplicación web que centraliza la consulta de cursos y la gestión posterior de las solicitudes de usuarios.

La documentación anterior describía un sistema de inventario, facturación y tecnologías que no corresponden al código disponible. La presente versión fue actualizada mediante revisión estática del repositorio local asociado a molstack-dev/Chef-Jonathan-Buitrago, incluida la estructura de vistas, scripts del cliente, API PHP y esquema creado por backend/init_db.php. Por tanto, el texto describe el estado implementado al 21 de julio de 2026, no una propuesta futura.

1. Descripción del problema

El negocio requiere un canal digital para presentar cursos y servicios de pastelería, recibir datos de contacto y solicitud de los interesados, registrar las inscripciones y controlar su estado de pago. También necesita que el usuario consulte sus servicios y que el administrador revise y procese las solicitudes generadas.

Sin un sistema centralizado, la información de clientes, reservas, comprobantes, estados de pago y solicitudes de reembolso puede quedar dispersa y ser difícil de consultar. La aplicación aborda ese problema al mantener dichos datos en una base relacional y exponerlos en paneles diferenciados para el usuario y el administrador.

2. Justificación

La solución concentra el catálogo, las solicitudes de servicio y el seguimiento de pagos en un solo entorno web. Para el cliente, reduce pasos de contacto al permitir registro, agenda y consulta del historial. Para el administrador, proporciona interfaces de administración de usuarios, cursos, contenido, inscripciones y reembolsos.

El valor de la implementación actual no reside en un módulo de inventarios ni en facturación electrónica, pues esos componentes no están presentes. Su alcance comprobable es la administración de la relación entre usuarios, oferta formativa y solicitudes de servicio, con trazabilidad básica mediante estados, fechas y comprobantes almacenados.

4. Alcance y delimitación

4.1 Alcance funcional implementado

  • Landing pública con información del chef, enlaces sociales y una muestra de cursos.
  • Catálogo dinámico de cursos/servicios con título, descripción, precio, duración, categoría, fecha de evento e imagen.
  • Registro, inicio de sesión, recuperación por pregunta de seguridad y cambio de contraseña.
  • Perfil de usuario con actualización de datos, pregunta de seguridad y preferencias de notificación.
  • Registro de asesorías, cursos y eventos; reserva con datos de identificación y fecha.
  • Registro y consulta de inscripciones, carga de comprobante y actualización administrativa de estado de pago.
  • Acceso al contenido activo de cursos pagados, seguimiento de progreso y emisión de datos para certificados cuando la inscripción está completada.
  • Historial de solicitudes y flujo de solicitud, cancelación, aprobación o rechazo de reembolsos.
  • Panel administrativo para usuarios, servicios, contenido, solicitudes e incidencias de reembolso.

4.2 Fuera de alcance

  • Inventario, compras, proveedores, códigos de barras, facturación electrónica y reportes contables: no existen tablas ni interfaces activas que los implementen.
  • Pasarela de pago integrada: el sistema conserva comprobantes y estados; no procesa transacciones bancarias o de tarjeta.
  • Despliegue cloud, AWS, Azure o arquitectura de microservicios: el repositorio está preparado para ejecución local con Apache/PHP y MySQL/MariaDB.
  • Notificaciones persistentes: existe un endpoint que intenta enviar correo con mail(), pero no hay tabla de notificaciones ni configuración de envío garantizada.

Nota de consistencia: los archivos clients.php, sellers.php y sus listados asociados permanecen en el repositorio, pero sus tablas no son creadas por init_db.php. Se consideran endpoints heredados y no forman parte del alcance operativo documentado.

5. Metodología de actualización documental

Se aplicó revisión estática y trazabilidad entre cuatro fuentes internas: (a) el repositorio Git configurado con el remoto del proyecto; (b) las páginas de views/ e index.html; (c) los scripts de assets/ que consumen la API; y (d) los archivos PHP de backend/, especialmente el inicializador de base de datos. Los requisitos y el diccionario se redactaron a partir de esas evidencias. No se infirieron módulos por el nombre de archivos que no tengan soporte en el esquema o la interfaz actual.

8.1 Consideraciones de seguridad y calidad

La implementación incluye bases importantes: hash de contraseñas, sesiones y sentencias preparadas. Sin embargo, la configuración local tiene credenciales por defecto para XAMPP y algunos endpoints requieren una revisión adicional para uniformar la autorización. Antes de producción se recomienda: variables de entorno obligatorias, HTTPS, control de tamaño/tipo de comprobantes, protección CSRF, registros de auditoría, pruebas automatizadas y revisión integral de permisos de cada endpoint.

10.2 Reglas de integridad y estados

  • users.email es único; los roles admitidos son admin y user.
  • Las inscripciones tienen estado operativo pending, confirmed o completed; el pago admite pending, paid, rejected, refund_requested y refunded.
  • Las asesorías manejan los tipos asesoria, curso y evento; su estado incluye además cancelled.
  • Los reembolsos tienen estado pending, approved o rejected.
  • Al eliminar un curso se eliminan sus inscripciones y contenidos por cascada. Las referencias de usuario en varias tablas se establecen en nulo al eliminar el usuario.

12. Instalación y operación local

  1. Instalar PHP 8.x, MySQL o MariaDB y un servidor web. Puede utilizarse Apache con XAMPP.
  2. Configurar, si es necesario, las variables DB_HOST, DB_USER, DB_PASS y DB_NAME. Por defecto se usa 127.0.0.1, usuario root, contraseña vacía y base chef_jonathan.
  3. Servir la carpeta del proyecto desde el servidor HTTP.
  4. Abrir backend/init_db.php una sola vez para crear la base e insertar los datos de demostración. Advertencia: el archivo elimina y recrea las tablas principales; no debe ejecutarse sobre datos reales sin una copia de seguridad.
  5. Abrir index.html a través de la URL del servidor, por ejemplo http://localhost/.

13. Hallazgos y trabajo futuro

La revisión detectó coherencia entre el modelo actual y los módulos de usuarios, servicios, inscripciones, contenido y reembolsos. También detectó elementos que requieren consolidación: endpoints heredados que dependen de tablas inexistentes en el inicializador, rutas de API expresadas de manera absoluta en algunos scripts, y una política de autorización no uniforme entre todos los endpoints.

Como mejoras futuras se recomiendan una batería de pruebas, migraciones versionadas en lugar de un inicializador destructivo, validación y almacenamiento seguro de archivos, manejo transaccional uniforme de pagos/reembolsos, auditoría de roles, una pasarela de pago si el negocio lo requiere y generación formal de certificados en PDF. Estas mejoras no se declaran como funcionalidades actuales.

Conclusiones

El proyecto implementa una plataforma web para la gestión de la oferta formativa y de servicios de Chef Jonathan Buitrago. Su núcleo funcional está compuesto por catálogo, autenticación, perfil, solicitudes de asesoría/evento, inscripciones, comprobantes de pago, contenidos de curso, progreso, certificados basados en finalización y reembolsos.

La arquitectura implementada es cliente–servidor y local: frontend HTML/CSS/JavaScript, backend PHP y MySQL/MariaDB mediante PDO. Esta conclusión se deriva directamente de los archivos del repositorio y reemplaza descripciones que mencionaban tecnologías o procesos no presentes.

La actualización deja una base documental útil para mantenimiento y evaluación académica porque establece los límites reales del sistema, explica sus flujos y relaciona cada módulo con las estructuras de datos y componentes de software que lo soportan.
